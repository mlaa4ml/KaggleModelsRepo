> Ветка: `anthropic-claude-opus-5-default`
> Базовая ветка: `main`
> Репозиторий: `mlaa4ml/KaggleModelsRepo` — «test some Kaggle models»

---

## 1. Что я увидел в репозитории

На момент написания документа в базовой ветке `main` фактически нет кодовой базы:
присутствует только `README.md` с описанием из двух строк («test some Kaggle models»).
Файлов `requirements.txt`, пакетов, ноутбуков или CI-конфигурации я не обнаружил.

Это важно для оценки моей роли: репозиторий находится на стадии «чистого листа»,
поэтому наибольшую пользу я приношу не точечными правками, а тем, что помогаю
заложить структуру проекта, в которую потом будут ложиться эксперименты с
Kaggle-моделями.

## 2. Как я работаю (ограничения инструментов)

Я взаимодействую с репозиторием исключительно через четыре инструмента:

| Инструмент | Что позволяет |
|---|---|
| `list_branches` | посмотреть список веток |
| `create_branch` | создать закреплённую за мной ветку |
| `read_file` | прочитать файл из базовой ветки `main` |
| `write_file` | создать/перезаписать файл **целиком** в моей ветке |

Отсюда следуют честные ограничения, о которых стоит помнить:

* **Я не выполняю код.** Я не могу запустить `pytest`, обучить модель, замерить
  метрику или проверить, что импорт действительно резолвится. Всё, что я пишу,
  проверяется только «глазами» — моими и ревьюера.
* **Я пишу файл целиком.** Патчей/диффов нет: чтобы изменить одну строку, я должен
  воспроизвести весь файл. Для больших файлов это риск потери фрагментов, поэтому
  я предпочитаю сначала прочитать файл, а потом переписать его полностью.
* **Я не удаляю и не переименовываю файлы**, не создаю PR и не мержу ветки.
  Итог моей работы — коммиты в ветке `anthropic-claude-opus-5-default`,
  которые человек ревьюит и вливает сам.
* **Я вижу только `main`.** Прочитать собственные ранее записанные файлы из своей
  ветки я не могу, поэтому веду работу так, чтобы каждый файл был самодостаточным.
* **Нет доступа к данным Kaggle.** Датасеты, `kaggle.json`, приватные лидерборды
  мне недоступны — я работаю с кодом и конфигурацией, а не с данными.

## 3. Какие изменения кода я способен вносить

### 3.1. Каркас проекта
* Разложить репозиторий по классической структуре ML-проекта:
  ```
  data/            # raw / interim / processed (в .gitignore)
  notebooks/       # исследовательские ноутбуки
  src/
    data/          # загрузка и подготовка данных
    features/      # генерация признаков
    models/        # обучение, инференс, чекпойнты
    validation/    # схемы кросс-валидации
    utils/         # сиды, логирование, тайминги
  configs/         # YAML-конфиги экспериментов
  tests/           # unit-тесты
  ```
* Написать `requirements.txt` / `pyproject.toml`, `.gitignore` (с исключением
  `data/`, `*.csv`, `*.pkl`, `.ipynb_checkpoints`, артефактов моделей),
  `Makefile` с целями `setup`, `lint`, `test`, `train`, `submit`.

### 3.2. Пайплайн работы с Kaggle-моделями
* Скрипты загрузки/кэширования датасета через Kaggle API (`src/data/download.py`).
* Модули препроцессинга: обработка пропусков, кодирование категорий
  (target/ordinal/one-hot), масштабирование, работа с датами и текстом.
* Единый интерфейс обучения для типовых бейзлайнов: логистическая регрессия,
  RandomForest, LightGBM / XGBoost / CatBoost, простые нейросети на PyTorch.
* Схемы валидации: `KFold`, `StratifiedKFold`, `GroupKFold`, `TimeSeriesSplit`,
  OOF-предсказания и честный расчёт метрик.
* Ансамблирование: усреднение, ранговое усреднение, взвешивание, стекинг.
* Генерация `submission.csv` строго по формату `sample_submission.csv`.

### 3.3. Инженерия и качество
* Конфигурируемость: вынос гиперпараметров в YAML + чтение через `argparse`/Hydra-подобный слой.
* Воспроизводимость: единая функция `set_seed()`, фиксация версий библиотек,
  логирование параметров и метрик каждого запуска в `experiments/`.
* Логирование вместо `print`, прогресс-бары, тайминги этапов.
* Unit-тесты на детерминированные куски: фичи, метрики, сплиты, формат сабмита.
* CI на GitHub Actions: установка зависимостей, `ruff`/`flake8`, `black --check`, `pytest`.
* Типизация (`typing`), докстринги, приведение стиля к PEP 8.

### 3.4. Рефакторинг и документация
* Перенос логики из ноутбуков в переиспользуемые модули `src/`.
* Устранение дублирования, разбиение «god-функций», выделение чистых функций.
* Расширение `README.md`: как поставить окружение, как запустить обучение,
  как получить сабмит, описание структуры каталогов.
* `CONTRIBUTING.md`, шаблоны PR/issue, `docs/` с описанием экспериментов.

## 4. Чего я делать не буду (или буду с оговорками)

* Не стану утверждать, что код «протестирован» — я его не запускал.
* Не буду выдумывать метрики, скоры лидерборда или результаты экспериментов.
* Не добавлю в репозиторий секреты (`kaggle.json`, токены) — только инструкции,
  как положить их в переменные окружения.
* Не буду коммитить тяжёлые артефакты (веса, датасеты) — для них `.gitignore`
  и внешнее хранилище.
* Не стану менять `main` напрямую: любые изменения — только через мою ветку.

## 5. Как я вижу свою роль

Я — **ML-инженер-помощник и «санитар» репозитория**. Автор проекта задаёт
направление: какое соревнование, какая метрика, какая идея. Я беру на себя
рутину, которая обычно съедает время между идеями:

1. **Строю леса вокруг эксперимента** — структуру, конфиги, скрипты запуска,
   чтобы новая гипотеза проверялась изменением одного YAML, а не копипастой ноутбука.
2. **Превращаю ноутбуки в код** — то, что уже сработало, переезжает в `src/`
   и покрывается тестами, чтобы не сломаться при следующей итерации.
3. **Держу воспроизводимость** — сиды, версии, логи запусков; чтобы результат
   недельной давности можно было повторить.
4. **Пишу документацию** — чтобы через месяц (или другому человеку) было понятно,
   что здесь происходит.
5. **Предлагаю варианты, а не диктую** — там, где есть развилка (LightGBM или
   CatBoost, target encoding или one-hot), я формулирую компромисс и оставляю
   выбор человеку.

Оптимальный режим взаимодействия: человек формулирует задачу и предоставляет
контекст (соревнование, метрика, формат данных) → я готовлю изменения в своей
ветке → человек запускает код локально/в Kaggle-ноутбуке и возвращает мне
ошибки и метрики → я итеративно правлю. Меня стоит воспринимать как быстрый,
аккуратный, но **непроверенный на исполнении** источник кода, который всегда
проходит через человеческое ревью.
