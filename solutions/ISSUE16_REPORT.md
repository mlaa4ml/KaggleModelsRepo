# Отчёт по доработке блокнота benchmark-task-agentic-github-v2bf642(1).ipynb (Issue #16)

Ветка: `google-gemini-3-5-flash-lite-issue-16`

В данном отчёте приводится подробный разбор 4 проблем и ограничений, описанных в issue #16, а также предлагаются готовые решения и архитектурные доработки для блокнота `benchmark-task-agentic-github-v2bf642(1).ipynb` (и связанных версий агента).

---

## 1. Сброс выбранной рабочей ветки между раундами

### Проблема
После вызова `create_issue_branch(N)` в раунде 1, в начале раунда 2 раннер может сбрасывать внутреннее состояние агента (контекст ядра или переменные сессии). В результате первый же вызов `write_file` в раунде 2 ошибочно уходит в дефолтную ветку (`anthropic-claude-opus-5-default` или аналогичную главную ветку модели), создавая лишние коммиты вне специализированной ветки `...-issue-N`.

### Решение
1. **Идемпотентный вызов в начале каждого раунда**: Обязательно вставлять `create_issue_branch(N)` первой строкой в раунде 2 и последующих.
2. **Архитектурное исправление в коде агента (ноутбука)**:
   - Внедрить персистентный класс `AgentContext`, сохраняющий текущую ветку и состояние сессии на диск в файл `kbench_agent_state.json`.
   - Добавить валидацию префикса ветки при ее установке (`set_branch`), чтобы агент не мог случайно переключиться на чужую или главную ветку.
   - Раннер должен инициализировать `AgentContext` единожды на всю сессию модели, а не пересоздавать его между раундами.

## 2. Чтение из `main` вместо рабочей ветки (`from_my_branch=True`)

### Проблема
Инструменты поиска и чтения (`list_files`, `search_code`, `read_file`) по умолчанию обращаются к ветке `main`, из-за чего агент не видит свежие изменения, сделанные им самим в рабочей ветке в предыдущих шагах или раундах.

### Решение
- Изменить сигнатуру и дефолтное поведение оберток GitHub-инструментов в коде блокнота: установить `from_my_branch=True` по умолчанию для всех операций чтения/поиска.
- Добавить в вывод инструментов явный префикс (например, `[branch: <slug>-issue-N]`), чтобы агент всегда понимал, откуда именно читаются данные.
- Реализовать инструмент `diff_vs_base()`, позволяющий агенту проверять свои изменения относительно `main` перед завершением работы.

## 3. Обрезка вывода (`MAX_TOOL_OUTPUT`) при чтении больших файлов (~50 КБ блокнотов)

### Проблема
Файлы ноутбуков (`.ipynb`) весят порядка 48–50 КБ, что значительно превышает лимит `MAX_TOOL_OUTPUT`. При попытке прочитать файл целиком `read_file` обрезает вывод, оставляя агенту неполный JSON, с которым невозможно работать.

### Решение
1. **Постраничный курсор (`gh_read_cursor`)**: Реализовать механизм чтения с параметрами `start_line` и `max_lines`, возвращающий в конце ответа указатель на следующий блок (`next_start_line=N из M` или `...[eof]`).
2. **Структурный инструмент `nb_outline`**: Добавить специальный инструмент для разбора `.ipynb`, который за один вызов возвращает оглавление ячеек (индексы, тип `markdown`/`code`, заголовки), экономя контекст.
3. **Точечное редактирование `nb_replace_cell(index, source)`**: Позволить агенту менять конкретную ячейку по ее индексу, не перезаписывая весь 50-килобайтный JSON файл целиком.

## 4. Отсутствие исполнения кода и создания issues

### Проблема
Агент в текущей реализации не имеет возможности запускать написанный код (проверять юнит-тесты) и создавать GitHub Issues программно.

### Решение
1. **Исполнение кода (`run_python`)**:
   - Добавить безопасную обертку для выполнения Python-скрипта в изолированном дочернем процессе с ограничением по времени (`timeout_sec`) и без передачи секретного токена репозитория в окружение запускаемого скрипта.
   - Добавить инструмент `run_repo_file(path, args)` для тестирования скриптов из репозитория.
2. **Создание Issues (`create_issue`)**:
   - Реализовать функцию отправки POST-запроса к GitHub API (`/repos/{owner}/{repo}/issues`) при наличии у токена соответствующих прав (scope `repo` / `issues:write`).
