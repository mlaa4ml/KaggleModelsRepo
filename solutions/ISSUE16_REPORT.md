# Отчёт по доработке блокнота benchmark-task-agentic-github-v2bf642(1).ipynb (Issue #16)

Ветка: `google-gemini-3-5-flash-lite-issue-16`

В данном отчёте приводится подробный разбор 4 проблем и ограничений, описанных в issue #16, а также предлагаются готовые решения и архитектурные доработки для блокнота `benchmark-task-agentic-github-v2bf642(1).ipynb` (и связанных версий агента).

---

## 1. Сброс выбранной рабочей ветки между раундами

### Проблема
После вызова `create_issue_branch(N)` в раунде 1, в начале раунда 2 раннер может сбрасывать внутреннее состояние агента (контекст ядра или переменные сессии). В результате первый же вызов `write_file` в раунде 2 ошибочно уходит в дефолтную ветку (`anthropic-claude-opus-5-default` или аналогичную главную ветку модели), создавая лишние коммиты вне специализированной ветки `...-issue-N`.

### Решение
1. **Идемпотентный вызов в начале каждого раунда**: Обязательно вставлять `create_issue_branch(N)` первой строкой в раунде 2 и последующих.
2. **Архитектурное исправление в коде агента (ноутбука)**:
   - Внедрить персистентный класс `AgentContext`, сохраняющий текущую ветку и состояние сессии на диск в файл `kbench_agent_state.json`.
   - Добавить валидацию префикса ветки при ее установке (`set_branch`), чтобы агент не мог случайно переключиться на чужую или главную ветку.
   - Раннер должен инициализировать `AgentContext` единожды на всю сессию модели, а не пересоздавать его между раундами.

---

## 2. Чтение из `main` вместо рабочей ветки (`from_my_branch=True`)

### Проблема
Инструменты поиска и чтения (`list_files`, `search_code`, `read_file`) по умолчанию обращаются к ветке `main`, из-за чего агент не видит свежие изменения, сделанные им самим в рабочей ветке в предыдущих шагах или раундах.

### Решение
- Изменить сигнатуру и дефолтное поведение оберток GitHub-инструментов в коде блокнота: установить `from_my_branch=True` по умолчанию для всех операций чтения/поиска.
- Добавить в вывод инструментов явный префикс (например, `[branch: <slug>-issue-N]`), чтобы агент всегда понимал, откуда именно читаются данные.
- Реализовать инструмент `diff_vs_base()`, позволяющий агенту проверять свои изменения относительно `main` перед завершением работы.

---

## 3. Обрезка вывода (`MAX_TOOL_OUTPUT`) при чтении больших файлов (~50 КБ блокнотов)

### Проблема
Файлы ноутбуков (`.ipynb`) весят порядка 48–50 КБ, что значительно превышает лимит `MAX_TOOL_OUTPUT`. При попытке прочитать файл целиком `read_file` обрезает вывод, оставляя агенту неполный JSON, с которым невозможно работать.

### Решение
1. **Постраничный курсор (`gh_read_cursor`)**: Реализовать механизм чтения с параметрами `start_line` и `max_lines`, возвращающий в конце ответа указатель на следующий блок (`next_start_line=N из M` или `...[eof]`).
2. **Структурный инструмент `nb_outline`**: Добавить специальный инструмент для разбора `.ipynb`, который за один вызов возвращает оглавление ячеек (индексы, тип `markdown`/`code`, заголовки), экономя контекст.
3. **Точечное редактирование `nb_replace_cell(index, source)`**: Позволить агенту менять конкретную ячейку по ее индексу, не перезаписывая весь 50-килобайтный JSON файл целиком.

---

## 4. Отсутствие исполнения кода и создания issues

### Проблема
Агент в текущей реализации не имеет возможности запускать написанный код (проверять юнит-тесты) и создавать GitHub Issues программно.

### Решение
1. **Исполнение кода (`run_python`)**:
   - Добавить безопасную обертку для выполнения Python-скрипта в изолированном дочернем процессе с ограничением по времени (`timeout_sec`) и без передачи секретного токена репозитория в окружение запускаемого скрипта.
   - Добавить инструмент `run_repo_file(path, args)` для тестирования скриптов из репозитория.
2. **Создание Issues (`create_issue`)**:
   - Реализовать функцию отправки POST-запроса к GitHub API (`/repos/{owner}/{repo}/issues`) при наличии у токена соответствующих прав (scope `repo` / `issues:write`).
# Отчёт по issue #16 — ограничения агентного слоя и их исправление

Агент: `anthropic/claude-opus-5@default`
Ветка: `anthropic-claude-opus-5-default-issue-16`
Добавленный ноутбук: `benchmark-task-agentic-github-claude-opus-5-issue16.ipynb`
(оригиналы `benchmark-task-agentic-github-v2bf642(1).ipynb` и
`benchmark-task-agentic-github-updated.ipynb` не изменялись)

---

## 1. Сброс рабочей ветки между раундами

**Диагноз.** Выбранная через `create_issue_branch(N)` ветка хранилась в переменной
одного прогона слоя инструментов. Раннер пересоздаёт объекты между раундами, поэтому
в раунде 2 первый `write_file` уходил в ветку по умолчанию `<slug>` — отсюда лишний
коммит `911c83b` (на `main` не влияет, guard по slug отработал).

**Исправление** (ячейка «Fix 1»):

* класс `AgentContext(slug, base)` — единственный владелец состояния;
* состояние дублируется на диск (`/kaggle/working/kbench_agent_state.json`),
  поэтому переживает не только границу раунда, но и рестарт ядра;
* `set_branch` запрещает любую ветку без префикса slug (guard остаётся жёстким);
* новые инструменты `current_branch()` и `use_branch(branch)` — дешёвая проверка
  и явное переключение;
* `ctx.round_header(i, n)` — строка «Текущая рабочая ветка: …», которую раннер
  обязан подставлять в промпт каждого раунда, чтобы модель не гадала;
* в раннере `ctx`/`tools` строятся **один раз на модель**, а не на раунд.

Дополнительно предлагается ужесточить критерий задачи `github_issue_resolution`:
проверять, что коммиты ушли именно в `<slug>-issue-<N>`, а не в `<slug>`.

## 2. Инструменты чтения смотрят в `main`

**Диагноз.** `list_files/search_code/read_file` по умолчанию читали базовую ветку,
из-за чего агент не видел собственных коммитов и рисковал перезаписать свою работу.

**Исправление** (ячейка «Fix 2», `build_read_tools(ctx)`):

* дефолт `from_my_branch=True` — читаем рабочую ветку;
* в первой строке ответа печатается `[branch: …]`, чтобы источник данных был явным;
* `from_my_branch=False` даёт базовую ветку (сравнение с `main`);
* `diff_vs_base()` печатает `ahead_by/behind_by`, файлы и сообщения коммитов.

## 3. `MAX_TOOL_OUTPUT` не даёт прочитать ~50 КБ ноутбук

**Диагноз.** `_clip` резал ответ молча, без указания позиции. Хуже того,
`benchmark-task-agentic-github-v2bf642(1).ipynb` минифицирован в одну строку —
постраничное чтение «по строкам» на нём не работает вовсе.

**Исправление** (ячейка «Fix 3»):

* `gh_read_cursor(path, branch, start_line, max_lines)` — набирает строки под
  бюджет вывода и всегда дописывает хвост `...[cursor] next_start_line=N из M`
  либо `...[eof]`; чтение продолжается следующим вызовом без потери файла;
* особый режим для файла из одной сверхдлинной строки: курсор считается в символах;
* `nb_outline(path)` — оглавление ноутбука (индекс, тип, размер, первая строка
  каждой ячейки): карта 50 КБ файла за один дешёвый вызов;
* `nb_cell(path, index)` — исходник конкретной ячейки;
* `nb_replace_cell(path, index, new_source)` — точечная правка ячейки без
  перезаписи всего JSON (сейчас правка ноутбука стоит десятки тысяч output-токенов
  и рискует затереть чужие изменения).

## 4. Нет исполнения кода и нет создания issues

**Исправление** (ячейка «Fix 4»):

* `run_python(code, timeout_sec)` — запуск в отдельном процессе, временный CWD,
  урезанный `env` (без `GITHUB_TOKEN`), таймаут; возвращает exit code, stdout, stderr;
* `run_repo_file(path, args, timeout_sec)` — скачать файл из ветки и выполнить
  (например, `solutions/issue13_text_stats.py` с самотестами);
* `create_issue(title, body, labels)` — `POST /issues`, нужен scope `Issues: RW`.

Ограничение, которое остаётся: `run_python` — это не полноценная песочница
(нет cgroups/seccomp), только изоляция процесса, таймаут и урезанное окружение.
Для бенчмарка этого достаточно; для недоверенного кода нужен контейнер.

---

## Как применить

Ячейки из `benchmark-task-agentic-github-claude-opus-5-issue16.ipynb` вставляются
после раздела 2 исходного ноутбука (слой `gh_*`) и до регистрации инструментов.
Точка входа — `build_toolset(slug)`: возвращает `(ctx, tools)`.
Функции-инструменты регистрировать через `functools.wraps`, иначе схема
инструмента вырождается в `{args, kwargs}` (известный баг проекта).

## Что проверено, а что нет

* Код написан по реально прочитанным исходникам ноутбука (`_gh_request`,
  `_gh_paginate`, `_clip`, `_err`, `gh_list_files`, `gh_read_file`, `gh_search_code`,
  `gh_write_file`, `gh_compare`, `gh_create_branch`) — имена и сигнатуры совпадают.
* Исполнить ноутбук у меня по-прежнему нет возможности (это и есть пункт 4 issue),
  поэтому код не запускался — он предлагается к ревью и прогону владельцем репозитория.
