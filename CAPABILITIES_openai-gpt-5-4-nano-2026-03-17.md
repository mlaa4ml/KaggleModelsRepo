# CAPABILITIES_openai-gpt-5-4-nano-2026-03-17

## Роль в этом проекте
Я — агент, который помогает запускать и улучшать бенчмарк `kaggle-benchmarks` для оценки «способности» LLM работать с GitHub-репозиторием через **ограниченный набор инструментов**.

В рамках этой задачи моя практическая цель — расширять «агентные возможности» в ноутбуке: добавлять новые инструменты/обёртки, делать их безопасными и воспроизводимыми, а также улучшать процесс интеграции с GitHub-воркфлоу (ветки, чтение/запись файлов, проверка прогресса).

## Что я способен(на) менять в коде проекта
Я могу:
1. **Дорабатывать ноутбук `benchmark_task_github_skill.ipynb`**: править логику генерации toolset’ов, добавлять новые инструменты и контролировать доступы/ограничения.
2. **Добавлять новые GitHub-инструменты в toolset**, используя REST API внутри ноутбука, например:
   - `list_issues` / `get_issue` / `comment_on_issue` (чтение issues и комментарии),
   - `create_pull_request` (если нужно),
   - `search_code`/`get_commit`/`get_file_history` (для дополнительного контекста).
3. **Усилить безопасность и корректность**:
   - жёстко ограничить, в какие ветки можно писать,
   - валидировать имена веток и пути файлов,
   - добавить rate-limit/ретраи с бэкоффом для устойчивости,
   - сделать идемпотентность для операций создания/обновления.
4. **Улучшать механику «раундов» и бюджетов**:
   - добавлять счётчики и логирование для каждого инструмента,
   - улучшать обработку partial-success (например, если комментарий удалось, а запись файла — нет).
5. **Предлагать и добавлять диагностические проверки**:
   - проверка прав токена (write/read) на небольших тестовых операциях,
   - preflight-проверки доступности нужных endpoints.

## Что я могу сделать в рамках текущих ограничений инструментария (в this-run)
В данном окружении у меня есть только инструменты репозитория: 
- `list_branches`, `create_branch`, `read_file`, `write_file`.

Поэтому в этой итерации я **не могу** напрямую:
- прочитать все issues через GitHub REST,
- оставить комментарий в issues,
- создать отдельные ветки по каждому issue и связать их комментариями.

Но я могу описать, как именно это должно быть реализовано в ноутбуке: расширить набор инструментов, чтобы **модели внутри ноутбука** могли делать это через GitHub REST API.

## Как я вижу требуемый итог (пункт 3 задания)
Чтобы агент мог:
1) читать **All issues**,
2) создавать **ветку на конкретное issue**,
3) писать **комментарий в соответствующее issue** с ссылкой на ветку,
нужно в ноутбуке сделать следующее.

### Предложение по архитектуре
- Добавить GitHub toolset’у новые функции:
  - `gh_list_issues(state="open", labels=None, per_page=100, page=...) -> str/JSON`
  - `gh_comment_on_issue(issue_number, body) -> str`
  - (опционально) `gh_get_repo_default_branch`, `gh_get_issue_comments_count`, и т.п.

- В `make_github_tools(...)` расширить список доступных инструментов, чтобы они работали в пределах текущей модели:
  - `read_file` по-прежнему читает строго из `GITHUB_BASE_BRANCH`,
  - `write_file/create_branch` пишут строго в ветку, назначенную этой модели, либо в ветку, привязанную к issue (если позволить модели выбирать slug).

### Как избежать «опасного» поведения
- Ввести whitelist на:
  - формат имени ветки (например, `issue-<n>-<model_slug>`),
  - допустимые пути для `write_file`.
- Добавить в инструмент-комментарий проверку, что issue номер — числовой и относится к текущему репозиторию.

### Что делать с тем, что сейчас есть жёсткая привязка ветки модели
Сейчас `create_branch`/`write_file` завязаны на `branch_name = slug(model_id)`.
Чтобы сделать пункт 3, есть два варианта:
1) **Сделать ветку issue внутри ветки модели** (например, ветки вида `model-slug/issue-123` невозможны как git ветка напрямую, зато можно использовать `model-<model_slug>-issue-123`). Тогда модель может создавать/писать в несколько веток.
2) **Убрать/смягчить жёсткую замыкалку** и разрешить модели создавать ветку по issue, но при этом ввести строгую валидацию и ограничение.

В обоих случаях нужно обновить контракт инструментов и критерий `task_check_fn`.

## План расширения возможностей (коротко)
