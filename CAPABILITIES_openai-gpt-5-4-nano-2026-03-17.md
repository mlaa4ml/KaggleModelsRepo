# Capabilities & Role — openai-gpt-5-4-nano-2026-03-17

## Что я умею делать в этом проекте
В рамках предоставленных инструментов я могу:

1. **Читать контекст репозитория**
   - Просматривать содержимое файлов (например, ноутбука для Colab/Kaggle) через `read_file`.
   - Понимать структуру пайплайна: загрузка данных, препроцессинг, обучение, валидация, экспорт артефактов.

2. **Вносить правки в notebook/ноутбук**
   - Создавать или обновлять файлы целиком через `write_file`.
   - Применять изменения по согласованному плану: например, заменить логику предобработки, добавить новый бейзлайн, улучшить метрики/логи, исправить ошибки пайплайна.

3. **Документировать изменения в отдельном артефакте**
   - Создавать markdown-файлы с описанием стратегии, различий и того, как повторить эксперимент.
   - Фиксировать: какие гиперпараметры были изменены, какие ожидания от изменения и как сравнивать результаты.

4. **Работать итеративно в отдельной ветке**
   - Выполнять все изменения в своей ветке, чтобы не загрязнять `main`.

## Какие изменения кода я способен(на) вносить
Я могу предлагать и реализовывать (в пределах имеющихся инструментов и текста ноутбука) следующие типы улучшений:

- **Тюнинг пайплайна**: корректировки предобработки, нормализации, кодировок категориальных признаков, обработки пропусков.
- **Улучшение тренировочного цикла**: ранняя остановка, контроль сидов, корректная кросс-валидация, настройка лосс-функций.
- **Повышение воспроизводимости**: единый набор seed’ов, фиксация версии зависимостей (в пределах ноутбука), логирование конфигурации.
- **Исправление багов**: несоответствие форматов данных, ошибки в селекторах колонок, утечки данных (data leakage), неправильные метрики.
- **Расширение базовых моделей/бейслайнов**: добавление новых вариантов моделей, ансамблирование, фиче-инжиниринг.
- **Стабилизация инференса**: приведение формата входа/выхода, корректный сохраненный артефакт, подготовка submission.

## Ограничения (что я НЕ могу сделать напрямую сейчас)
- Я **не могу** автоматически читать/обрабатывать *все* issues репозитория или писать комментарии в issues, потому что в текущем наборе инструментов нет функций для работы с GitHub Issues.
- Я **не могу** исполнять код или запускать ноутбук: доступ ограничен чтением/записью файлов.
- Я **не могу** создавать частичные патчи: `write_file` заменяет файл целиком (поэтому для небольших правок лучше заранее аккуратно прочитать файл и затем записать обновлённый полный контент).

## Как я вижу свою роль в процессе развития репозитория
Моя роль — быть **инженером по улучшению экспериментов** в Kaggle/Colab-ноутбуках:
- превращать цель из issue (“улучшить метрику/добавить модель/исправить ошибку”) в конкретный план изменений,
- аккуратно вносить правки в notebook в отдельной ветке,
- сопровождать результат описанием: что изменилось, почему, как проверить.

## Что нужно добавить, чтобы я смог(ла) закрывать цикл с issues
Чтобы реализовать вашу конечную цель (“читать All issues и делать изменения по задаче из issues, после комментировать с ссылкой на ветку”), нужны дополнительные инструменты, например:

1. **Работа с issues**
   - `list_issues` (или `search_issues`) — получить список/контент всех issues.
   - `read_issue` — читать конкретный issue.
   - `create_issue_comment` — оставить комментарий в issue.

2. **Ветвление под задачу**
   - Уточняющий механизм для веток: например, автоматическое формирование имени ветки из номера issue.
   - Возможность создавать новую ветку без коллизий, если одна и та же ветка уже занята.

3. **(Опционально) Обновление статуса/PR**
   - Если в репозитории требуется PR: инструменты для `create_pull_request` и `request_review`.
   - Но даже без PR достаточно комментария в issue со ссылкой на ветку.

## Как бы я выполнял работу по issue (целевой процесс)
1. Загружу список issues и выберу подходящую по приоритету/готовности.
2. Прочитаю контекст: описание issue и (при необходимости) соответствующие части ноутбука.
3. Создам ветку (например, `issue-<number>-<short-title>`).
4. Внесу изменения в notebook, сохранив воспроизводимость.
5. Верну результат: комментарий в issue с ссылкой на ветку и кратким changelog’ом.
